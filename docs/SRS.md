# Software Requirements Specification — AI Ops Coordinator

Status: draft v0.1, bootstrapped ahead of unit U0.
This document is read-only input to every unit's planning step. Units may propose
amendments via an ADR; they do not edit this file directly.

## 1. Introduction

AI Ops Coordinator observes a host machine and, optionally, one or more PostgreSQL
instances running on it, and answers two questions an operator actually has:
"is something wrong?" and "is it the database, or is it the box?" Where safe and
approved, it can also change a small number of tunable settings and verify whether
the change helped.

## 2. Scope & Product Vision

In scope: telemetry collection, deterministic performance/security analysis, an
optional AI explanation layer, a policy-gated action executor, a thin console client,
and (v2) a fleet coordinator. Out of scope for v1: multi-DBMS support beyond
PostgreSQL, automatic failover, GPU/NPU telemetry, and any AI-originated action
execution. See the prompt pack's "Cut" list for the authoritative exclusions.

## 3. Definitions & Acronyms

- **Core**: the local Rust service (`rust_core/service`) exposing the API.
- **Console**: the thin client UI consuming the core's API.
- **Agent**: headless v2 component reusing core logic, reporting to a Coordinator.
- **Capability**: a reported ability level — Supported / Limited / Unavailable /
  PermissionRequired — never a fabricated value standing in for missing data.
- **Evidence**: a {metric, value, threshold, window} tuple backing any verdict.

## 4. System Context & Users

Primary user: an operator or SRE running one machine or a small fleet. Secondary
user: the AI explanation layer, which consumes the same evidence structures as the
console and has no privileged access. All functional requirements below are tagged
with a stable FR-ID; units implementing them must reference the ID in code comments
sparingly and in tests explicitly (see docs/TRS.md §45, Testing Strategy).

## 5. FR-SYS — Core Service Requirements

- FR-SYS-001: The core exposes a single local API surface, versioned, over a
  transport that is not reachable from the network by default.
- FR-SYS-002: The core reports its own resource usage on every health check.
- FR-SYS-003: The core degrades sampling frequency under host resource pressure
  rather than compounding the problem it is trying to observe.

## 6. FR-CPU — CPU Monitoring

- FR-CPU-001: Per-core and aggregate utilization, load averages, frequency where
  exposed, and context-switch/interrupt rates.
- FR-CPU-002: Utilization must be computed from a monotonic clock delta, not wall
  time, and must report `SampleGap` rather than a misleading rate across a gap.

## 7. FR-MEM — Memory Monitoring

- FR-MEM-001: Total, used, available, cached/buffered, swap, and a deterministic
  pressure classification NORMAL/ELEVATED/HIGH/CRITICAL.
- FR-MEM-002: Inside a container, report the cgroup limit as the ceiling, not the
  host total, and flag `containerized: true`.

## 8. FR-STO — Storage Monitoring

- FR-STO-001: Per-volume capacity, free space, and I/O rates (read/write bytes and
  ops per second) with counter-reset detection.
- FR-STO-002: I/O latency where the platform exposes it; otherwise Unavailable with
  a reason, never a synthesized value.

## 9. FR-NET — Network Monitoring

- FR-NET-001: Per-interface throughput, packet counts, and error/drop counts, with
  counter-reset detection (a NIC counter reset must never present as negative
  throughput).

## 10. FR-PRO — Process Monitoring

- FR-PRO-001: Enumerate running processes with CPU%, memory (RSS), owner, and
  command line where permitted.
- FR-PRO-002: Per-process disk and network I/O are reported only where the platform
  and permissions allow it; otherwise the capability model applies — no fabricated
  zeros.
- **FR-PRO-003**: Each process is classified into a documented, deterministic
  category enum (e.g. SYSTEM, USER_APPLICATION, BACKGROUND_SERVICE, DBMS_ENGINE,
  UNKNOWN) using a fixed rule set (path, owner, cgroup, known executable names).
  Classification must be unit-testable without a live process table.

## 11. Performance Analysis — Host & Database Bottleneck Classification

This section is the specification for the differentiator implemented in unit U5.

- FR-PERF-001: The core classifies the host bottleneck, when one exists, into
  exactly one of NONE / CPU / MEMORY / STORAGE_IO / NETWORK / THERMAL / POWER /
  BACKGROUND / MULTIPLE / UNKNOWN, using deterministic thresholds only.
- FR-PERF-002: Every classification carries an evidence list: each item names the
  metric, its observed value, the threshold that was crossed, and the time window
  the observation covers. A verdict with no evidence is invalid.
- FR-PERF-003: When a monitored PostgreSQL instance is present, the core also
  classifies database health (connection saturation, latency, slow queries, lock
  waits, deadlocks, rollback ratio, temp file usage, long transactions, replication
  lag, bloat proxies, availability) on the same evidence model.
- FR-PERF-004: Host score and database health score are each 0–100, computed from a
  frozen, versioned weight set (`score_version`). Weights are never user-configurable
  and historical rows are never re-scored when weights change — a new version is
  introduced instead.
- FR-PERF-005: No component of host or database scoring, or of bottleneck
  classification, may be produced or influenced by an AI model. This is a hard
  boundary, not a default.

## 12. FR-DEV — Device Monitoring

- FR-DEV-001: Enumerate attached storage, removable, and peripheral devices with a
  trust flag distinguishing previously-seen from newly-attached devices.

## 13. FR-HIST — Historical Data Requirements

- FR-HIST-001: History is queryable over last hour / 24h / 7d / 30d / a custom
  range, and the server — not the client — selects the correct retention tier.
- FR-HIST-002: Every persisted analytical row (performance, security, action,
  benchmark) is immutable once written; corrections happen via new rows, not updates.

## 14. FR-CAP — Capability & Degradation Model

- FR-CAP-001: Every metric family has a capability state: Supported, Limited,
  Unavailable, or PermissionRequired, each carrying a human-readable reason.
- FR-CAP-002: The capability registry is a single source of truth consumed by both
  the server (to decide what to report) and generated documentation (to describe
  what the product can do on a given platform). The console renders capability state
  directly — it never infers "no data" from an absent field.

## 15. FR-CONSOLE — Console / Operator UI Requirements

- FR-CONSOLE-001: The console contains no business logic — no thresholds, no
  scoring, no classification. It renders what the server sends.
- FR-CONSOLE-002: The console distinguishes, in the UI, between "value is zero" and
  "value is unavailable" and between "stale/gap" and "current."

## 16. FR-AI — AI Explanation Layer, General Requirements

- FR-AI-001: The AI layer is optional; every other requirement in this document
  must be satisfiable with the AI provider absent, unreachable, or misbehaving.
- FR-AI-002: The AI layer receives only an evidence bundle built by the deterministic
  analysis layer (§11) plus a numbered candidate list; it never receives raw
  credentials or the means to execute an action.
- FR-AI-003: AI output is constrained to a closed schema (summary, observations,
  recommendations, risk, confidence). Any field outside the schema is discarded.
- FR-AI-004: Any action-shaped content in an AI response references a
  `candidate_id` from the bundle, never a free-form identifier (PID, session id,
  table name) constructed by the model.
- **FR-AI-005**: Every numeric value in an AI response must carry an `evidence_ref`
  that resolves to an entry in the evidence bundle that produced it. A response
  containing an unreferenced numeric is rejected in its entirety — not partially
  used. This requirement must be testable by an automated validator, not by prompt
  wording alone.

## 17. Policy — Risk Classification

- FR-POL-001: Every action type has a documented risk level (INFORMATIONAL through
  PROHIBITED) and this mapping is exhaustive — an action type with no assigned risk
  cannot exist in a shipped build.
- FR-POL-002: Risk level, together with environment (§18), determines whether an
  action is auto-allowed, requires approval, or is denied.

## 18. Policy — Approval Workflow

- FR-POL-003: Actions above INFORMATIONAL risk require an explicit, single-use,
  time-limited approval bound to the specific action, target identity, and
  parameter set proposed. Any deviation (different target, mutated parameters,
  expired approval, replayed approval) is rejected.
- FR-POL-004: Production environments are never more permissive than development
  environments for the same action type.
- FR-POL-005: Every policy decision — including denials, expiries, and rejections —
  is written to the audit log (§20 in TRS for the chain design).

## 19. Policy — Protected Resources

- FR-POL-006: A registry of protected processes, protected services, trusted
  devices, and critical infrastructure is consulted by the policy engine — never by
  ad hoc checks at the call site — before any mutating action is approved or
  executed.

## 20. Security Event Detection

- FR-SEC-001: Security-relevant conditions are detected by deterministic rules
  operating on telemetry (and, where a DBMS is monitored, on DBMS-side signals per
  §34), each rule carrying an id, a documented rationale, and tunable thresholds.
  No detector may depend on an AI model to fire.
- FR-SEC-002: Detected events carry a severity (INFO..CRITICAL) and related events
  are correlated into a single incident rather than reported as unrelated noise.
- FR-SEC-003: A security-relevant flag on a resource overrides any performance-
  motivated action targeting that resource — enforced as a policy rule, not as UI
  copy or convention.
- FR-SEC-004: No response action may disable a firewall or antivirus product; this
  is a closed-enum guarantee, not a runtime check.
- FR-SEC-005: False positives are manageable per-rule and per-resource, with a
  recorded audit trail of suppressions and dismissals.

## 21. FR-BENCH — Benchmark & Rollback Requirements

- FR-BENCH-001: No "improved" or "regressed" verdict may be issued from a single
  point-in-time measurement; a verdict compares two sampling windows meeting a
  minimum duration and sample count, with a stability check on the baseline window.
- FR-BENCH-002: The honest default outcome is INCONCLUSIVE, and it is displayed with
  equal visual weight to a positive outcome — never buried.
- FR-BENCH-003: Any action applied for benchmarking purposes is reversible or
  explicitly labeled otherwise before it is applied, and rollback re-verifies target
  identity before acting.

## 22. FR-TUNE — Performance Tuning & Profiles

- FR-TUNE-001: A tuning profile is a declarative desired-state description, never an
  executable script, and is realized only through actions that independently pass
  policy (§17–19).
- FR-TUNE-002: At most one tuning plan may be in flight per target at a time.
- FR-TUNE-003: Fully-automatic action (AUTO_LOW_RISK) is limited to actions that are
  reversible, low risk, and have a locally recorded history of improved outcomes.

## 23. Non-Functional — Reliability & Availability

- NFR-REL-001: Loss of the AI provider, the monitored DBMS, or any single peripheral
  data source degrades the affected feature only; it must never crash the core or
  block unrelated telemetry.
- NFR-REL-002: A failed database migration never drops or recreates data; it blocks
  only the repository layer while live telemetry continues to serve.

## 24. Non-Functional — Portability

- NFR-PORT-001: The core's platform-specific code is isolated behind one trait
  (`PlatformAdapter`); unimplemented platform capabilities report Unsupported rather
  than failing to compile or silently returning zero.
- NFR-PORT-002: macOS support uses public APIs only; capabilities requiring
  Apple-granted entitlements are explicitly out of scope for v1.x.

## 25. Non-Functional — Privacy & Data Handling

- NFR-PRIV-001: SQL text is stored and forwarded to any AI provider in normalized,
  fingerprinted form by default in all environments; raw SQL requires explicit
  per-connection opt-in.
- NFR-PRIV-002: Credential material is never persisted in plaintext in any
  application-controlled store; it is enforced by type at the storage layer, not by
  code-review convention.

## 26. DBMS Monitoring — General & Connectivity

- FR-DB-001: Version, uptime, and reachability of each configured PostgreSQL
  instance, collected on a bounded poll interval with an explicit statement
  timeout and idle-in-transaction timeout on every connection the tool opens.
- FR-DB-002: The tool's own footprint against the monitored instance is minimized —
  one idle connection between polls is the target steady state.
- FR-DB-003: Extensions the tool depends on for a capability (e.g.
  pg_stat_statements) are detected, not assumed; a missing extension degrades that
  capability to Limited/Unavailable with a reason. The tool never issues
  `CREATE EXTENSION`.

## 27. DBMS Monitoring — Sessions & Connections

- FR-DB-004: Active sessions with a state classification (active, idle,
  idle-in-transaction, waiting), and connection pool saturation relative to
  `max_connections`.

## 28. DBMS Monitoring — Query Performance

- FR-DB-005: Query-level statistics where `pg_stat_statements` is present,
  normalized and fingerprinted per §25 (Privacy).

## 29. DBMS Monitoring — Locks & Blocking

- FR-DB-006: Lock waits and blocking chains, sufficient to identify the blocking
  session/query, not merely the blocked one.

## 30. DBMS Monitoring — Storage, Tables & Indexes

- FR-DB-007: Table and index size and statistics, dead-tuple/bloat proxies, and
  temp-file activity per session/statement where available.

## 31. Cross-Layer Correlation (Host ↔ DBMS)

- FR-CORR-001: Given host telemetry (§6–§13) and database telemetry (§26–§34) over
  the same time window, the core produces ranked root-cause hypotheses, each with
  supporting evidence, a confidence value computed from evidence strength by a
  documented formula, and an explicit list of causes that were considered and ruled
  out with the reason why.
- FR-CORR-002: The hypothesis set distinguishes, at minimum: DB locks, DB
  configuration, connection exhaustion, slow SQL, host CPU, host memory, storage
  latency, network, and client-side application behavior.
- FR-CORR-003: Correlation output uses the same contract types the console and the
  AI explanation layer consume — there is exactly one representation of "what the
  evidence shows."

## 32. DBMS Monitoring — Replication

- FR-DB-008: Primary/standby topology, LSN positions (sent/write/flush/replay), lag
  in both bytes and seconds, replication slot retention risk, and standby
  disconnection — alerted on trend, not threshold alone.

## 33. DBMS Monitoring — Configuration & Temp Files

- FR-DB-009: A curated set of operationally relevant GUCs (not the full
  configuration surface) is read and reported, plus temp-file byte/count activity
  as a memory-pressure proxy for query execution.

## 34. DBMS Security Events

- FR-DBSEC-001: Deterministic detection of repeated authentication failure, newly
  granted superuser/role privileges, permission changes, connections from unusual
  client addresses, and configuration changes — feeding the same incident model as
  §20.

## 35. FR-FLEET — Fleet & Coordinator Requirements (v2)

- FR-FLEET-001: An agent operates headlessly and continues local buffering when
  disconnected from the coordinator, backfilling without unbounded local growth.
- FR-FLEET-002: The coordinator never performs automatic replica promotion or
  automatic failover; these remain human-approved actions indefinitely.
- FR-FLEET-003: Role-based access control (see TRS §46) is enforced server-side;
  the console/agent boundary is never treated as a security boundary.

## 36. Traceability

Every FR-ID in this document must appear in the traceability matrix produced by
unit U15 (FR-ID → implementing unit → module → test). An FR-ID with no test is a
release blocker, not a documentation gap.
